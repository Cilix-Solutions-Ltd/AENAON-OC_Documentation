# Getting started

[Repository home](../README.md) · [Tool catalogue](TOOL_CATALOGUE.md) · [Access and use](ACCESS_AND_USE.md)

This route is for selected Open Call beneficiaries working within their approved activities. Repository access provides documentation; it does not create a hosted workspace, API entitlement or software licence.

1. **Identify the activity.** Use the [catalogue](TOOL_CATALOGUE.md) to choose one or several tools for your approved use case. Consult the [integration overview](INTEGRATION_OVERVIEW.md) if tools may be used together.
2. **Read each tool profile.** Check prerequisites, inputs, access model, dependencies and limitations before planning deployment or data sharing.
3. **Agree the scope with the provider.** Confirm the project/workspace, user roles, permitted data, outputs and any API need. Use your assigned project onboarding contact or [info@aenaon-project.eu](mailto:info@aenaon-project.eu) for routing to the responsible provider.
4. **Obtain access through the authorised channel.** The provider supplies relevant credentials, endpoints, manuals or deployment resources where applicable. Receive and store credentials securely outside this repository.
5. **Prepare permitted inputs.** Confirm ownership, confidentiality and permission to share. Agree sanitised, synthetic or representative data when operational data cannot be shared. Never commit credentials or sensitive infrastructure information.
6. **Follow the supplied instructions.** Begin with an agreed representative activity and confirm that the expected result is available. Report access or documentation issues to the provider through the onboarding route, without including secrets.

## Which access route applies?

| Route | What to arrange |
| --- | --- |
| Provider-hosted browser/API service | The provider provisions controlled access and confirms roles, scope and any authorised API documentation. Repository access alone is insufficient. |
| Provisioned virtual environment | Agree the environment and operator roles with the provider. For the cyber range, administrators configure and launch scenarios with the Digital Twin dependency. |
| Explicitly supplied deployment artefacts | Use only packages or images authorised and supplied by the owner, with its prerequisites and instructions. A Docker-based architecture does not mean public images or unrestricted deployment are available. |

xBOMGuard, the Risk Assessment Platform, CTIP, the CILIX Workbench, the Threat Detection & Incident Response Platform and SCTIP are provider-operated services. Do not plan self-managed installation of these services. ZELUS confirms the resources and access arrangements for its Digital Twin, ASAT and cyber range tools.

## Before testing or monitoring

Agree explicit authorisation for targets and security assessments, and prior authorisation for live operational telemetry or monitoring. Confirm data handling and permitted recipients of findings. See [access and use](ACCESS_AND_USE.md) and the [FAQ](FAQ.md).
