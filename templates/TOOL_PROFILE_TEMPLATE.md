# Tool profile template

[Repository home](../README.md) · [Contribution instructions](../CONTRIBUTING.md)

Copy the nine sections below into the relevant `tools/` directory and replace each instruction with complete, approved prose. Use the official tool name as the document title. Remove instructional text before proposing a published profile. Use relative links for repository navigation. Do not infer availability, endpoints or deployment rights from architecture descriptions.

## 1. Overview

State the tool name, responsible provider, service family and main function. Identify the technical source and any approved version-specific scope. Retain the common Technical Annex baseline unless an owner-confirmed update is agreed with CILIX.

## 2. Potential Open Call use

Describe suitable activities within an approved beneficiary use case, without promising outcomes or requiring use of every tool.

## 3. Access and deployment

Describe provider-hosted, provisioned-environment or explicitly authorised deployment arrangements. Separate documentation access, browser access, API access and downloads. State relevant exclusions for proprietary services.

## 4. Getting started

Explain prerequisites, permitted data preparation and the provider onboarding route. Add installation steps only when verified and authorised by the owner. If resources are supplied during onboarding, say so directly rather than inserting missing-content fields or dummy links.

## 5. Inputs and outputs

List supported input information and expected result types. Do not imply that every format or export is available to every user; identify confirmed conditions.

## 6. Interfaces and dependencies

Identify only documented interfaces and required components. Describe potential integrations as conditional unless explicitly agreed. Explain any external runtime, connectors or telemetry requirements.

## 7. Documentation and resources

Link approved manuals, release resources, API documentation or external material when supplied. Verify destination, version, intended audience, licensing and redistribution permission. Keep owner-supplied technical guides in the tool directory where appropriate. If links are unavailable, explain the authorised onboarding route in usable prose.

## 8. Limitations and authorised use

State relevant technical, licensing and data-handling boundaries, testing/monitoring authorisation and deployment exclusions. Do not add new legal terms or override project/provider agreements. Never include credentials, confidential datasets or live infrastructure information.

## 9. Support and updates

Name the responsible provider and approved support/onboarding route. Use the supplied project contact for routing where no provider contact has been supplied. Explain how that provider proposes updates for CILIX approval. Do not invent contacts or GitHub identities.
